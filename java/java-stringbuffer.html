Java StringBuffer と StringBuilder クラス

文字列を変更する場合には、StringBuffer と StringBuilder クラスを使用する必要があります。

String クラスとは異なり、StringBuffer と StringBuilder クラスのオブジェクトは何度も変更でき、新しい未使用オブジェクトを生成しません。

StringBuffer クラスを使用する場合、毎回 StringBuffer オブジェクト自体に対して操作が行われ、新しいオブジェクトは生成されません。そのため、文字列を変更する必要がある場合は StringBuffer の使用が推奨されます。

StringBuilder クラスは Java 5 で導入されました。StringBuffer との最大の違いは、StringBuilder のメソッドがスレッドセーフではない（同期アクセスができない）ことです。

StringBuilder は StringBuffer よりも速度面で優れているため、ほとんどの場合 StringBuilder クラスの使用が推奨されます。

例

public class RunoobTest{ public static void main(String[] args){ StringBuilder sb = new StringBuilder(10); sb.append("Runoob.."); System.out.println(sb); sb.append("!"); System.out.println(sb); sb.insert(8, "Java"); System.out.println(sb); sb.delete(5,8); System.out.println(sb); } }

上記の例をコンパイルして実行した結果は次のとおりです。

Runoob..
Runoob..!
Runoob..Java!
RunooJava!

ただし、アプリケーションがスレッドセーフを要求する場合は、StringBuffer クラスを使用する必要があります。

Test.java ファイルコード：

public class Test{ public static void main(String[] args){ StringBuffer sBuffer = new StringBuffer("Runoob 公式サイト："); sBuffer.append("www"); sBuffer.append(".runoob"); sBuffer.append(".com"); System.out.println(sBuffer); } }

上記の例をコンパイルして実行した結果は次のとおりです。

    Java では StringBuffer と String には一定の違いがあります。まず、String は final で修飾されているため、その長さは不変です。String の concat メソッドを呼び出しても、それは文字列を連結して新しいオブジェクトを生成し、連結後の String の値を新しく生成したオブジェクトに代入するだけです。一方、StringBuffer の長さは可変であり、StringBuffer の append メソッドを呼び出すことで StringBuffer の長さを変更できます。また、StringBuffer と比較すると、String は長さが変化すると非常にメモリを消費します。

    Java における StringBuilder と StringBuffer はどのようなシナリオに適していますか？

    最も簡単な答えは、StringBuffer には基本的に適用シーンがないということです。本当にスレッドセーフが必要なシナリオに遭遇しない限り、すべての場合において StringBuilder を選択すべきです。もし遭遇したなら、必ずここにコメントで知らせてください。

    そして、一点補足します。スレッドセーフについてですが、仮に本当にそのようなシナリオに遭遇したとしても、残念ながら、おそらく 99.99....99% の場合、StringBuffer を選択する必要はありません。StringBuffer のスレッドセーフは、JVM が例外をスローせずにスムーズに実行を継続することを保証するだけであり、論理の正しさや呼び出し順序の正しさを保証するものではないからです。ほとんどの場合、私たちが必要とするのはスレッドセーフだけではなく、ロックです。

    最後に、なぜ StringBuffer が存在するのでしょうか。本当に価値がないのなら、なぜ JDK がこのクラスを提供するのでしょうか。答えは非常に簡単です。最初は StringBuilder が存在しなかったからです。Sun の人々は、どのような愚かな考えからか、StringBuffer をスレッドセーフにすると決めました。そして約10年後、人々はこれがなんと愚かな決定であったかをようやく認識し、この10年間にその愚かな決定が「Java の実行速度が遅い」という噂にどれほどの力を与えたかを認識しました。そこで、JDK 1.5 のときに、ついに非スレッドセーフな StringBuffer 実装を提供し、それを StringBuilder と名付けました。ちなみに、javac もおそらくこのバージョンから、プラス記号で連結されるすべての文字列演算を暗黙的に StringBuilder に書き換えるようになりました。つまり、JDK 1.5 以降、プラス記号で文字列を連結してもパフォーマンスの損失はまったくありません。

    多くのコメントで指摘されているように、私が上で述べた「プラス記号で文字列を連結してもパフォーマンスの損失はまったくない」という表現は厳密ではありません。厳密に言うと、ループがない場合、1行でプラス記号を使って文字列を連結するのはパフォーマンスの損失がありません。Java コンパイラは暗黙的に StringBuilder に置き換えます。しかし、ループがある場合、コンパイラは十分に賢い置き換えができないため、やはり不要なパフォーマンス損失が発生します。したがって、ループで文字列を連結するときは、素直に StringBuilder を使いましょう。
