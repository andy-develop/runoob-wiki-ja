Ollama モデル管理

この章では、Ollama のモデル管理コマンド（プル、確認、コピー、削除）と、モデルのメモリ常駐メカニズムについて説明します。

モデルのプル：ollama pull

pull コマンドはモデルのダウンロードのみを行い、会話は開始しません。事前にモデルを準備しておくのに適しています。

デフォルトタグ（latest）をダウンロード：

ollama pull qwen3.5

指定サイズのタグをダウンロード：

ollama pull qwen3.5:4b

実行すると、標準のダウンロード進行状況の出力が表示されます：

$ ollama pull qwen3.5:4b
pulling manifest
pulling 87497c5f0e8f... 100% |████████████████████| 3.4GB
verifying sha256 digest
writing manifest
success

ダウンロードが中断しても最初からやり直す必要はありません。Ollama はレイヤーごとに検証して保存するため、同じコマンドを再実行すると未完了のレイヤーが自動的に再開されます。

また、ollama run には pull のロジックが組み込まれています。モデルを初めて実行する際にダウンロードと読み込みが自動的に完了するため、日常的には個別に pull を実行する必要はほとんどありません。

異なるサイズのタグは、公式があらかじめ作成した異なるモデルファイルに対応しています。pull 時に量子化精度を追加指定することはできません。自分で大きなモデルを小さいサイズに圧縮したい場合は、create コマンドで量子化を行う必要があります。これについては Modelfile カスタマイズの章で説明します。

ローカルモデルの確認：list と show

list はローカルの全モデルとディスク使用量を一覧表示する、最もよく使われる確認コマンドです。

ローカルモデルの一覧表示：

ollama list

例：

$ ollama list
NAME               ID            SIZE      MODIFIED
qwen3.5:0.8b       9e3f4b3a1c2d  1.0GB     5 minutes ago
qwen3.5:4b         b1c7d9e2f3a4  3.4GB     2 days ago
qwen3.5:latest     a8b2c9d3e4f5  6.6GB     2 hours ago

4つの列はそれぞれモデル名、バージョンフィンガープリント、ディスク使用量、最終更新時刻です。ディスク容量が逼迫した際は、SIZE 列で確認するのが最も直接的です。

特定のモデルの詳細を確認したい場合は、show コマンドを使用します：

# 查看模型详情：能力、参数、系统提示词、许可证等
ollama show qwen3.5

show はいくつかの典型的な疑問に答えてくれます：このモデルはどのような機能（会話、視覚、ツール呼び出し）に対応しているか、デフォルトの生成パラメータは何か、システムプロンプトの内容、コンテキストウィンドウのサイズなどです。

さらに応用的な使い方として、モデルの完全な構成を Modelfile としてエクスポートできます：

例

# モデルのレシピをエクスポート。これを基に修正して独自のモデルを再構築できる
ollama show --modelfile qwen3.5

この「レシピの確認 → 修正 → 再構築」という流れは、Modelfile カスタマイズの章で詳しく説明します。

実行中のモデルの確認：ollama ps

list はディスクを確認し、ps はメモリを確認します：どのモデルが読み込まれているか、どのくらい占有しているか、いつアンロードされるか。

例

# 現在メモリ/VRAM に読み込まれているモデルを一覧表示
ollama ps
$ ollama ps
NAME             ID            SIZE      PROCESSOR    CONTEXT    UNTIL
qwen3.5:9b       a8b2c9d3e4f5  9.6GB     100% GPU     131072     4 minutes from now

各列の意味は以下の通りです：

列名意味
NAME / IDモデル名とバージョンフィンガープリント。list と同じ
SIZEそのモデルが現在占有している総メモリ（メモリと VRAM を含む）
PROCESSOR読み込み位置：100% GPU は完全に GPU 上にあることを示し、100% CPU は完全にメモリ上にあることを示します。48%/52% CPU/GPU のような比率が表示される場合は、VRAM が不足してモデルが分割されていることを意味します。
CONTEXT現在割り当てられているコンテキストウィンドウのサイズ
UNTIL自動アンロードまでの残り時間（keep-alive のカウントダウン）

PROCESSOR 列は「モデルがなぜ遅いのか」を調査するための最初の確認ポイントです。100% GPU でない限り、モデルが完全に VRAM に読み込まれていないことを示します。性能最適化の具体的な方法は GPU と性能の章で詳しく説明します。

コピーとリネーム：ollama cp

cp は既存のモデルに新しい名前を付けます。リネームやスナップショットの保存によく使われます。

例

# 新しい名前のモデルをコピーして作成
ollama cp qwen3.5:4b runoob-test

# 通常のモデルと同じように使用
ollama run runoob-test

非常に実用的な応用テクニックがあります：モデルに「名前を借りる」方法です。

一部のツールはモデル名をハードコードしています（例：gpt-3.5-turbo）。cp でローカルモデルをこの名前にコピーすれば、そのようなツールでローカルモデルを直接使用できます：

例

# ローカルモデルをツールが期待する名前にコピー
ollama cp qwen3.5 gpt-3.5-turbo

cp はほぼ瞬時に完了します。元のモデルファイルを指す新しいモデル名リストを作成するだけで、ディスク上に数 GB のデータを複製するわけではないからです。

モデルの削除とディスククリーンアップ：ollama rm

rm はローカルモデルを削除し、モデルライブラリが「入るばかりで出てこない」問題の解決策です。

例

# 指定したモデルを削除
ollama rm qwen3.5:0.8b
$ ollama rm qwen3.5:0.8b
deleted 'qwen3.5:0.8b'

ディスクをクリーンアップする推奨手順は、まず ollama list で容量が大きく使用していないモデルを特定し、その後 1 つずつ rm を実行することです。

複数のタグが同じ基盤ファイルを共有している場合、1 つのタグを削除しても他のタグの通常の使用には影響しません。

cp で名前を借りたモデルも忘れずに処理してください：元のモデルを削除しても、借名コピーは存在し続けて容量を占有します。目に見えないディスクのブラックホールにしないようにしましょう。

モデルの停止と keep-alive 常駐メカニズム

まずモデルのライフサイクル図を見ると、各管理コマンドがどの段階で機能するかが一目でわかります。

重要なメカニズムは keep-alive です：モデルは会話終了後すぐにはアンロードされず、デフォルトでメモリまたは VRAM に 5 分間常駐します。

この 5 分以内に再度リクエストがあれば、モデル読み込みの待ち時間なしで応答します。時間を超えて新しいリクエストがなければ、自動的にアンロードされメモリが解放されます。

モデルにすぐにリソースを解放させたい場合は、stop コマンドで手動アンロードします：

例

# 指定したモデルをすぐにアンロード
ollama stop qwen3.5:4b

常駐時間の調整方法は 3 つあります：

方法操作適用シーン
グローバルデフォルトを変更環境変数 OLLAMA_KEEP_ALIVE を設定します（例：30m、2h）サーバーで統一された常駐ポリシーを適用したい場合
リクエストごとに指定API 呼び出し時に keep_alive パラメータを渡します。-1 は常駐してアンロードしないことを意味しますアプリケーション層でモデルごとに使い分けたい場合
