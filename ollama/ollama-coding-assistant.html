Ollama ローカル AI プログラミングアシスタント

この章では、コーディング専用のローカルモデル「runoob-coder」をカスタマイズし、VS Code と Claude Code に接続して、完全オフラインでトークン費用がかからないプログラミングアシスタントを構築します。

中心となる作業は3つ：コードモデルを正しく選ぶこと、コーディング用Modelfileを適切に書くこと、使い慣れたツールに接続することです。

ステップ1：コードモデルを選ぶ、VRAMが決める

コードモデルの能力差は対話モデルよりも顕著ですが、参入障壁も高くなります。VRAMに応じて選びましょう：

あなたのハードウェア推奨モデル期待される性能
24GB以上のVRAMqwen3-coder専用コードモデル、ファイル横断の理解力が最強；30B級パラメータはVRAM要件が高く、長いコンテキストにはさらなる余裕が必要
16GBメモリ・専用GPUなしqwen3.5:9b カスタム版日常の補完、コード解説、ユニットテスト作成に十分
8GBメモリの旧マシンqwen3.5:4b / 0.8b カスタム版軽量なQ&A向き、複雑なタスクはクラウドに任せる

VRAMが足りず qwen3-coder を実行できなくても心配無用：:cloud タグでクラウド版を直接呼び出せます。コードに機密性のあるチームは、先にコンプライアンスチェックを済ませましょう。

ハードウェアに応じてプルします：

ollama pull qwen3-coder        # 24GB+ 显存
ollama pull qwen3.5:9b         # 16GB 内存

ステップ2：コーディングシナリオ用のModelfileを書く

素のモデルでもコードは書けますが「プロフェッショナル」ではありません——コメントなし、脱線しがち、フォーマットも適当。Modelfile でコーディング規範を固定化しましょう：

例

# ファイルパス：Modelfile
# VRAM 24GB+ の場合はベースを qwen3-coder に変更
FROM qwen3.5:9b

SYSTEM """
あなたは RUNOOB チームのプログラミングアシスタントです。以下の規範を守ってください：
1. 断片ではなく、完全でそのまま実行できるコードを優先して提示する
2. 各重要なステップに中国語のコメントを書き、「なぜ」を説明するなぜ"
3. PEP 8（Python）または言語の公式スタイルに従う
4. 不慣れなAPIに関わる場合は公式ドキュメントを確認するよう促し、インターフェースを捏造しない
5. 回答構成：考え方を一言 - コード - 注意事項
"""

# コードシナリオでは安定性が必要、ランダム性を低く抑える
PARAMETER temperature 0.2

# Agent/エディタシナリオではコードコンテキストが大きい、ウィンドウを十分に確保する
PARAMETER num_ctx 65536

専用コーディングモデルを構築：

ollama create runoob-coder -f Modelfile

「調整が十分か」を検収するには、3つの標準タスクでテストします：関数をそのまま使える状態にする（完全性を確認）、落とし穴のある古いコードを解説する（理解力を確認）、ユニットテスト作成を依頼する（規範順守を確認）。3つすべて合格してからエディタに接続しましょう。

num_ctx 65536 はエディタと Agent シナリオ向けです：ファイル全体や複数ファイルをコンテキストに入れるためです。VRAMが不足する場合は 32768 に下げ、ollama ps で PROCESSOR が依然として 100% GPU かどうかを確認してください。

ステップ3：エディタに接続する

カスタムモデルと素のモデルは、ツールから見れば違いはありません。接続方法は第11篇と完全に同じです。

VS Code Chat への接続

Ollama 公式拡張機能をインストール後、Chat のモデルセレクターで runoob-coder を選択するだけです。他の設定は不要です。

Claude Code への接続

例

# ワンクリック方式
ollama launch claude --model runoob-coder

# 手動方式：環境変数でローカルを指定し、モデル名にはカスタムモデルを使用
export ANTHROPIC_AUTH_TOKEN=ollama
export ANTHROPIC_BASE_URL=http://localhost:11434
claude --model runoob-coder

接続後、Claude Code のファイル編集、コマンド実行、複数ターンのリファクタリング機能はすべてローカルモデルが駆動します。長時間のタスクを実行する前に、コンテキストウィンドウが上記の設定になっているか確認してください。

効果の比較とモデル切り替え戦略

タスクに応じて異なる規模のモデルを使うべきです。選択戦略を固定化して、毎回迷わないようにしましょう：

タスクタイプ推奨モデル理由
関数補完、コード解説、ユニットテスト作成runoob-coder（ローカル）高速、無料、プライバシー保護
ファイル横断のリファクタリング、複雑なデバッグqwen3-coder またはクラウド最上位モデルより強力な長文コンテキスト理解が必要
バッチ生成、スクリプト処理ローカル小モデル + APIゼロコストで大量処理

切り替えコストが十分に低くて初めて、実際に切り替えることが可能になります：

例

# ターミナル対話中に終了せず直接モデルを切り替え
/load qwen3-coder

# VS Code ではモデルセレクターでクリック選択するだけ
# Claude Code 起動時に --model で指定

実用的な組み合わせ戦略：日常の90%のリクエストはローカルの小モデルに任せ、本当に難しい問題に直面したときだけ大モデルやクラウドモデルに切り替えます。Ollama のマルチタグ共存により、この「階層型」戦略は切り替えコストが一切かかりません。
