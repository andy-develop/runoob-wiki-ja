Dockerの基本概念

コンテナ化技術とは

コンテナはホストのカーネルを共有し、軽量で分離され、効率的であり、仮想マシンのように完全なオペレーティングシステムを必要としません。下図は Docker コンテナの基本アーキテクチャを示しています。

  • 上層 は複数のコンテナ（App A〜F）で、各コンテナが独立して1つのアプリケーションを実行します。
  • 中間層 は Docker で、これらのコンテナを管理します。
  • 下層 はホストOS（Host OS）とインフラストラクチャで、コンテナにハードウェアとシステムのサポートを提供します。

1、従来のアプリケーションデプロイの問題点

従来のアプリケーションデプロイでは、以下のような問題によく遭遇します。

  • 環境の不一致：アプリが開発環境では正常に動作するが、テスト環境や本番環境で問題が発生する
  • 依存関係の管理が複雑：異なるアプリが異なるバージョンのランタイムやライブラリファイルを必要とする
  • リソース利用率が低い：従来の仮想マシンは完全なOSが必要なため、多くのリソースを消費する
  • デプロイが複雑：環境の手動設定や依存関係のインストールが必要で、エラーが発生しやすい

2、コンテナ化技術による解決策

コンテナ化技術は以下の方法でこれらの問題を解決します。

  • 環境の標準化：アプリとその依存関係を一緒にパッケージ化し、どの環境でも一貫して動作することを保証する
  • 軽量：コンテナはホストOSのカーネルを共有するため、仮想マシンより軽量
  • 高速デプロイ：コンテナは数秒で起動でき、デプロイ効率が大幅に向上する
  • 可搬性：一度ビルドすれば、どこでも実行できる

3、コンテナ化の核心理念

コンテナ化は「イミュータブルインフラストラクチャ」の理念に従います。

  • アプリと環境はイミュータブルなイメージとしてパッケージ化される
  • 毎回のデプロイで同じイメージを使用する
  • 設定は環境変数または設定ファイルを通じて注入する
  • 問題の修正は実行中のコンテナを変更するのではなく、イメージを再ビルドすることで行う

Docker の中核概念

1、イメージ (Image)

定義：イメージは読み取り専用のテンプレートであり、アプリの実行に必要なすべてのもの（コード、ランタイム、ライブラリファイル、環境変数、設定ファイル）を含みます。

特徴：

  • レイヤーストレージ：イメージは複数のレイヤーで構成され、各レイヤーが1回の変更を表します
  • 読み取り専用性：イメージ自体は読み取り専用であり、直接変更できません
  • 再利用可能：同じイメージから複数のコンテナを作成できます
  • バージョン管理：タグ（tag）によるバージョン管理

例えて理解する：イメージはインストーラーやテンプレートのようなもので、アプリの実行に必要なすべてを定義しますが、それ自体は直接実行できません。

2、コンテナ (Container)

定義：コンテナはイメージの実行インスタンスであり、軽量で可搬性のある実行環境です。

特徴：

  • 分離性：各コンテナは独自のファイルシステム、ネットワーク、プロセス空間を持ちます
  • 一時性：コンテナは作成、起動、停止、削除ができます
  • 書き込み可能レイヤー：コンテナはイメージの上に書き込み可能なレイヤーを追加します
  • プロセスレベル：コンテナ内では通常1つのメインプロセスが実行されます

例えて理解する：イメージがクラスなら、コンテナはオブジェクトインスタンスです。1つのイメージから複数のコンテナを作成できるのは、1つのクラスから複数のオブジェクトを作成できるのと同じです。

3、リポジトリ (Repository)

定義：リポジトリはイメージを保存・配布する場所であり、1つのイメージの複数バージョンを含むことができます。

分類：

  • パブリックリポジトリ：Docker Hub など、誰でも利用できる
  • プライベートリポジトリ：企業内部で構築し、プライベートなイメージを保存するために使用
  • 公式リポジトリ：ソフトウェアの公式が保守するイメージリポジトリ

Registry vs Repository：

  • Registry：レジストリサーバー（Docker Hub など）
  • Repository：具体的なイメージリポジトリ（nginx、mysql など）

3、使用シナリオの比較

仮想マシンの適用シナリオ：

  • 完全な分離環境が必要な場合
  • 異なるオペレーティングシステムのアプリを実行する場合
  • ハードウェアレベルのセキュリティ分離が必要な場合

Dockerコンテナの適用シナリオ：

  • マイクロサービスアーキテクチャ
  • CI/CDパイプライン
  • アプリの迅速なデプロイとスケーリング
  • 開発環境の標準化

Docker の利点と適用シナリオ

主な利点

1. 環境の一貫性

  • 解決する問題：「私のマシンでは動く」問題
  • 実現方法：アプリと環境を一緒にパッケージ化する
  • 価値：環境関連のバグやデプロイ問題を減らす

2. 軽量で高効率

  • リソース利用：仮想マシンより少ないリソースで済む
  • 起動速度：秒単位の起動時間
  • 密度：1台のマシンでより多くのアプリインスタンスを実行できる

3. 可搬性

  • クロスプラットフォーム：Linux、Windows、macOS をすべてサポート
  • クラウドネイティブ：さまざまなクラウドプラットフォーム間で移行可能
  • ハイブリッド環境：ローカルで開発し、クラウドにデプロイ

4. バージョン管理とロールバック

  • イメージバージョン：各バージョンに対応するイメージがある
  • 迅速なロールバック：問題発生時に素早く前のバージョンに戻す
  • A/Bテスト：異なるバージョンを同時に実行して比較

5. 拡張性

  • 水平スケーリング：より多くのコンテナインスタンスを迅速に作成
  • 弾性スケーリング：負荷に応じてコンテナ数を自動調整
  • マイクロサービス：サービスの分割と独立したデプロイ

代表的な適用シナリオ

1. マイクロサービスアーキテクチャ

  • サービス分割：各マイクロサービスを独立してコンテナ化
  • 独立デプロイ：サービスを独立に更新および拡張できる
  • 技術スタックの自由：異なるサービスで異なる技術を使用できる

2. CI/CDパイプライン

  • ビルド環境：標準化されたビルド環境
  • テストの分離：各テストを独立したコンテナで実行
  • デプロイの一貫性：同じイメージを異なる環境にデプロイ

3. 開発環境の標準化

  • クイックセットアップ：新メンバーが素早く開発環境を取得
  • バージョン同期：チームが同じ開発環境を使用
  • 依存関係管理：ローカル環境の競合を回避

4. アプリケーションのモダナイゼーション

  • レガシーシステム：従来のアプリケーションをコンテナ化
  • クラウド移行：アプリケーションのクラウドプラットフォームへの移行を支援
  • ハイブリッドクラウド：異なるクラウド環境間での移植

Docker アーキテクチャの構成要素

全体アーキテクチャ図

Docker Client

機能：

  • ユーザーがDockerと対話する主な方法
  • ユーザーコマンドを受け取り、Docker Daemonに送信する
  • リモートのDocker Daemonと通信可能

よく使うコマンド：

  • docker run- コンテナを実行する
  • docker build- イメージを構築する
  • docker pull- イメージをプルする
  • docker ps- コンテナの状態を確認する

Docker Daemon

機能：

  • Dockerのコアサービスプロセス
  • イメージ、コンテナ、ネットワーク、ストレージボリュームを管理
  • Docker APIリクエストを監視して処理する

主な責務：

  • イメージ管理（ビルド、保存、配布）
  • コンテナライフサイクル管理
  • ネットワーク管理
  • データボリューム管理
  • Registryとの通信

Docker Engine

構成：

  • Docker Client + Docker Daemon + REST API
  • Dockerのコアコンポーネント

ワークフロー：

  1. ClientがDaemonにコマンドを送信する
  2. Daemonがコマンドを解析して実行する
  3. Registryと連携する（必要に応じて）
  4. ローカルのイメージとコンテナを管理する
  5. 結果をClientに返す

Docker Registry

役割：

  • Dockerイメージの保存と配布
  • イメージのバージョン管理を提供
  • パブリックリポジトリとプライベートリポジトリをサポート

Docker Hubの特徴：

  • 公式のパブリックRegistry
  • 多数のプリビルド済みイメージを含む
  • 自動ビルド機能をサポート
  • 無料および有料サービス

Docker の発展の歴史

重要なマイルストーン

  • 2013年：Dockerがオープンソースとして公開
  • 2014年：Docker 1.0がリリースされ、本番環境で利用可能に
  • 2016年：Docker Swarmがリリースされ、オーケストレーション機能を内蔵
  • 2017年：DockerがCE（コミュニティ版）とEE（エンタープライズ版）に分かれる
  • 2019年：Docker Desktopがリリースされ、開発者体験が向上

エコシステムの発展

  • コンテナオーケストレーション：Kubernetesが事実上の標準となる
  • コンテナランタイム：containerd、CRI-Oなどの代替ソリューション
  • イメージ形式：OCI標準の策定
  • セキュリティツール：コンテナのセキュリティスキャンおよび監視ツール
