Electron セキュリティ

Electron は組み合わせておりNode.js とブラウザ環境を、これによりデスクトップアプリの機能は非常に強力になりますが、一定のセキュリティリスクももたらします。
適切なセキュリティポリシーにより、XSS、リモートコード実行（RCE）、データ漏洩のリスクを低減できます。

セキュリティチェックリストとよくあるセキュリティリスク

セキュリティチェックリスト

  • 有効にするコンテキスト分離（contextIsolation）
  • 使用するプリロードスクリプト（preload.js）で安全な API を公開する
  • レンダラープロセスで Node.js モジュールを直接使用しない
  • 有効にするサンドボックスモード（sandbox: true）
  • 設定するコンテンツセキュリティポリシー（CSP）
  • IPC を安全に使用し、送信元と入力を検証する
  • アプリのシステム権限へのアクセスを制限し、最小権限の原則に従う
  • 信頼できないリモートコンテンツの読み込みを避ける

よくあるセキュリティリスク

  • リモートコンテンツの注入：未知の URL や HTML ファイルを読み込むと、悪意のある JS が実行される可能性がある
  • 安全でない IPC 呼び出し：レンダラープロセスが任意のメインプロセスメソッドを呼び出せる
  • Node.js の任意実行：レンダラープロセスで有効にするとnodeIntegrationシステムコマンドの実行に悪用される可能性がある
  • XSS 攻撃：ユーザー入力がページに直接レンダリングされる
  • 依存関係の脆弱性：更新されていないサードパーティライブラリを使用している

コンテキスト分離（Context Isolation）

contextIsolation の詳細

コンテキスト分離により、レンダラープロセスとメインプロセスは異なる JS 環境で実行されます。
レンダラープロセスのウェブページ JS は Node.js API に直接アクセスできず、安全なプリロードスクリプトを介してインターフェースを公開します。

const mainWindow = new BrowserWindow({
  webPreferences: {
    contextIsolation: true,  // 启用上下文隔离
    preload: path.join(__dirname, 'preload.js'),
    nodeIntegration: false   // 禁止在渲染进程使用 Node.js
  }
})

なぜコンテキスト分離が必要か

  • 読み込んだウェブページやサードパーティスクリプトによる Node.js への直接アクセスを防ぐ
  • 攻撃者が XSS を介してシステム権限を取得するのを防ぐ
  • レンダラープロセスは UI のみを処理し、メインプロセスがシステム操作を処理するようにする

分離されたコンテキストへの移行

  • 使用してcontextBridge.exposeInMainWorld安全な API を公開する
  • すべてのシステム操作をメインプロセスに置き、IPC を介して呼び出す

例：

// preload.js
const { contextBridge, ipcRenderer } = require('electron')

contextBridge.exposeInMainWorld('api', {
  getData: () => ipcRenderer.invoke('get-data')
})

レンダラープロセスは呼び出しのみを行いwindow.api.getData()、オペレーティングシステムを直接操作できません。

サンドボックスモード（Sandbox）

サンドボックスの有効化

サンドボックスモードでは、レンダラープロセスがブラウザの通常のウェブページのように動作し、Node.js 環境から完全に分離されます。

const mainWindow = new BrowserWindow({
  webPreferences: {
    sandbox: true,
    contextIsolation: true,
    preload: path.join(__dirname, 'preload.js')
  }
})

サンドボックスの制限と対策

  • 制限：レンダラープロセスは Node.js モジュールに直接アクセスできない
  • 対策：IPC を介してメインプロセスが提供する安全なメソッドを呼び出す
  • 利点：セキュリティが向上し、悪意のあるスクリプトによるシステム破壊を防ぐ

コンテンツセキュリティポリシー（CSP）

CSP は、ウェブページが読み込めるリソースの送信元を制限することで、XSS やデータインジェクション攻撃を防ぐことができます。

CSP 設定例

<meta http-equiv="Content-Security-Policy" content="
  default-src 'self';
  script-src 'self';
  style-src 'self' 'unsafe-inline';
  img-src 'self' data:;
  connect-src 'self' https://api.example.com;">

説明：

  • default-src 'self'：デフォルトでは同一オリジンのリソースのみ許可する
  • script-src 'self'：ローカルスクリプトのみ許可する
  • style-src 'self' 'unsafe-inline'：インラインスタイルを許可する
  • connect-src：AJAX / WebSocket リクエストのドメインを制限する

XSS 攻撃の防止

  • レンダラープロセスで直接使用してはいけないinnerHTMLユーザー入力の表示
  • ユーザー入力をエスケープするか、フレームワークのテンプレートを使用してレンダリングする

安全な IPC 通信

メッセージ送信元の検証

メインプロセスはレンダラープロセスの送信元を区別し、任意実行を避ける必要があります。

例：

ipcMain.handle('do-action', (event, data) => {
  if (event.senderFrame.url.startsWith('file://')) {
    // 安全来源，执行操作
  } else {
    console.warn('不安全的 IPC 请求被阻止')
  }
})

入力検証

  • IPC を介して渡されるすべてのデータは、型と範囲を検証する必要があります
  • 悪意のあるコマンドやファイルパスの注入を防ぐ
function validateInput(data) {
  if (typeof data !== 'string' || data.length > 100) throw new Error('非法输入')
  return data
}

最小権限の原則

  • レンダラープロセスに必要な機能のみを公開する
  • すべての Node.js API やシステム権限を公開しない
  • プリロードスクリプトを使用してインターフェースのアクセス範囲を制御する

まとめ

Electron セキュリティのベストプラクティスの核心は分離＋検証＋権限制限：

  • 分離：コンテキスト分離とサンドボックスモードを有効にする
  • 検証：CSP、XSS 対策、IPC 入力検証
  • 権限制限：レンダラープロセスの権限を最小限にし、必要な API のみを提供する

これらの原則に従うことで、デスクトップアプリが攻撃されたりデータが漏洩したりするリスクを大幅に低減できます。
